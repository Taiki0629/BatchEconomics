# 02. 実験設計

作成: 2026-07-28（P2）/ R-02 セルフレビュー（独立サブエージェント査読・指摘16件）反映済み
前提: `01_background.md` の仮説 H1〜H6 を検証する。無償枠は Chat completions 3,000 req/月（基盤モデル無償プラン）。

## 1. 実験の骨格

| 要素 | 設計 | 理由 |
|---|---|---|
| API | `POST /v1/chat/completions`（OpenAI 互換） | 主題のリクエスト課金対象。仕様確認済み |
| モデル | `gpt-oss-120b`（第一候補） | 通常提供モデルで入れ替わりリスクが低く、記事の再現性が高い。利用不可なら `llm-jp-3.1-8x13b-instruct4` に切替（D-006） |
| タスク | 日本語短文レビューの感情2値分類（positive / negative） | 正解が機械採点でき、バッチ化が自然で、読者が追試しやすい |
| データ | 自作 96 アイテム（ラベル明確な短文、48/48 均衡） | ライセンス問題なし・正解の曖昧さを排除・96 は水準 {1,2,4,8,16,32,48,96} すべてで割り切れる |
| バッチサイズ B | 1, 2, 4, 8, 16, 32 の 6 水準（**右打ち切り対策: C(B) が B=32 まで単調減少なら B=48, 96 を追試**。§2.4） | 2 倍刻みで U 字の形状を捉える。B=1 が基準線 |
| プロンプト形式 | `json_array` / `jsonl` の 2 形式 | H6。入出力の構造だけ変え、指示内容は共通化 |
| 試行 | B=1 は 1 trial、B∈{2,4,8} は 3 trial、B∈{16,32} は 6 trial | temperature=0 では B=1 の複数 trial は同一リクエストの反復（擬似反復）になるため 1 回に削減。大バッチはリクエスト単位指標の n 確保のため増量 |
| パラメータ | `temperature=0.0`、`stream=false`、`max_tokens` は**全水準共通の固定値**（試走の実測最大出力トークン × 安全係数 3、B=32 実測に基づく） | max_tokens を B 比例式にすると、reasoning トークンによる途中切断が B と交絡し H1・H2 を汚染するため固定値とする。`seed` は API 仕様に記載がないため使わない |

### 1.1 タスク・データセットの詳細

- 96 アイテム = 易しい 60（明確な賞賛・不満）+ 紛らわしい 36（否定表現・逆接・条件付き評価）
- 紛らわしい例を混ぜる理由: 正解率が天井（100%）に張り付くと H4（位置効果）が検出できない。目標は B=1 で正解率 90〜97% 程度に落ち着く難度
- LLM が作る「紛らわしい」文は LLM にとって紛らわしくない恐れがある（楽観バイアス）。**試走 p3-001 で B=1 の少数サンプル正解率を粗く確認し、天井なら紛らわしい 36 件を差し替える**（試走枠 30 req 内で実施）
- 各アイテムは `{"id": "d-001", "text": "..."}`。正解ラベルは別ファイル（プロンプトに混入させない）
- データは `90_resources/dataset/sentiment_96.jsonl`、作成規約と難度内訳は同ディレクトリの README に記録

### 1.2 プロンプト 2 形式（H6）

共通指示（システムプロンプト・日本語）: 「各レビューを positive / negative に分類。**入力に含まれる id をそのまま返す**。全アイテムについて必ず 1 件ずつ出力。説明文・コードフェンス禁止」

| | json_array | jsonl |
|---|---|---|
| 入力 | `[{"id":"d-001","text":"..."}, ...]` を1つの JSON 配列で渡す | 1行1アイテムの JSON オブジェクトを改行区切りで渡す |
| 要求する出力 | `[{"id":"d-001","label":"positive"}, ...]` の JSON 配列のみ | `{"id":"d-001","label":"positive"}` を1行ずつ |
| パース | 全体を `json.loads`（コードフェンスは剥がしてから。剥がした事実はログに記録） | 行ごとに `json.loads`。壊れた行があっても他の行は回収（部分回収数を記録） |

シャッフルシードは **2 形式で共有**する（同じ trial は同じバッチ構成・順序で両形式に流す）。形式比較を対応付きにするためだが、H4 に使える独立シャッフル数が半減する事実は限界として記録する。

### 1.3 採点・集計の定義

**アイテム単位（形式間で対称な主要指標）**
- `回収アイテム`: 復元できた出力のうち、送信した id と一致するもの。**アイテム回収率 = 回収数 ÷ items_sent**
- `correct`: 回収され、かつ label が正解（`positive`/`negative` の完全一致、大文字小文字は正規化）
- 重複・余剰の規則: 同一 id が複数返された場合は**最初の 1 件のみ採用**（重複件数 `dup_id_count` をログ）。送信していない id は無視（`unknown_id_count` をログ）

**リクエスト単位（形式ごとの補助指標）**
- json_array: `parse_ok`（配列全体の復元成否）— H2 の json_array 側指標
- jsonl: **行単位破損率**（破損行数 ÷ 出力行数）— H2 の jsonl 側指標。`parse_ok` は「1 行以上復元」とし全滅検知用
- `finish_reason` を必ず記録し、`length`（max_tokens 切断）由来の失敗は**「切断失敗」として別カテゴリ集計**。H2 の分析は切断失敗を除いた系列と含めた系列の両方を示す（切断は設定ポリシーの帰結であり、モデルの生成品質と区別する）

**実効コスト C(B)（H1 の主指標）**
- **プール比を主とする**: C(B) = その水準×形式の総消費リクエスト数（リトライ含む）÷ 総 correct
- **形式別に算出・描画し、B* も形式別に報告する**（プールすると H6 が真のとき B* が無意味になる）
- trial 単位の C はばらつきの点プロット表示のみに使う。correct=0 の trial は C=∞（全滅）として件数を別掲し、平均計算から除外
- 比の平均は総計比より上方バイアスするため（Jensen）、trial 平均を主表示にしない

**位置効果（H4）**
- 分析対象は **parse 回収に成功したアイテムのみ**（リクエスト全滅は pos 一様喪失で勾配を希釈するため除外し、全滅は H2/H3 側で扱う）
- B≥8 の水準で、バッチ内位置 pos を四分位に区切り正解率を比較。アイテム難度（易/紛らわしい）で層別
- **検出力の限界を明記**: 目標正解率 93〜95% では誤答総数が少なく、小さい位置効果（1〜3pp）は本設計の n では検出できない。検出されない場合は「検出可能だった効果量の下限」を逆算して記事に報告する。検出力向上が必要なら P4 予備枠で B=32 の trial を追加（§2.4）

**レイテンシ（H5）**
- 定義: 成功 attempt のリクエスト送信〜レスポンス完了までの時間（送信間インターバルの sleep は含まない）。リトライがあった場合は最終成功 attempt の値を使い、失敗 attempt の時間は別途記録
- H5 の検証は「**アイテム当たりレイテンシ = リクエスト完了時間 ÷ B が B とともに減少するか**」に絞る。リクエスト当たりレイテンシは記述的に示すのみ（自己回帰生成では B にほぼ線形なのは自明で反証可能性が弱いため）
- reasoning トークン量がレイテンシを支配する可能性は限界として記録

**区間推定**
- 同一 96 アイテムを全条件で再利用するため観測は独立でなく、二項比率の Wilson CI は過小幅になる。**アイテムを再抽出単位とするクラスターブートストラップ（percentile、2,000 回）**を目安区間とし、その旨を図注に明記。厳密な検定はしない（記述統計中心と記事に明記）

**リトライ運用コストの外挿（P4 分析項目）**
- 本実験はコンテンツ失敗をリトライしない設計（D-008）のため、実測 C(B) は「リトライしない運用」のコスト。実測した失敗率 p(B) から「失敗バッチを成功までリトライする運用」の期待コストをモデル計算（幾何級数）で外挿し、両方を記事に示す

### 1.4 リトライと「失敗の扱い」（重要）

- **パース失敗・欠落・不正解はリトライしない**。それ自体が測定対象のデータである（D-008）
- リトライするのはトランスポート層の失敗のみ: 429 / 5xx / タイムアウト（指数バックオフ、上限 5 回、`sakura-ai` スキル準拠）
- リトライも 1 リクエストとして消費計上（C(B) の分子に入る）
- **停止条件はリトライ上限より優先**: 429 が 3 連続 → run 全体を停止し状況確認（無償枠超過の可能性）
- リクエスト間隔: 最低 1.0 秒（レート制限閾値が非公開のため安全側）

## 2. 消費リクエスト見積もり（承認対象）

### 2.1 本実験の計算

1 trial・1 形式あたりのリクエスト数（96 アイテムを処理）: `96/B`

| 水準 | trial 数/形式 | req/形式 | req 両形式 |
|---|---|---|---|
| B=1 | 1 | 96 | 192 |
| B=2 | 3 | 48×3=144 | 288 |
| B=4 | 3 | 24×3=72 | 144 |
| B=8 | 3 | 12×3=36 | 72 |
| B=16 | 6 | 6×6=36 | 72 |
| B=32 | 6 | 3×6=18 | 36 |
| **計** | | **402** | **804** |

| 項目 | 計算 | リクエスト数 |
|---|---|---|
| 試走（p3-001） | 疎通・モデルID・reasoning 挙動・max_tokens 校正・データ難度確認 | **30** |
| 本実験（p3-002） | B=1〜8 の部分: 192+288+144+72 | **696** |
| 大バッチ（p3-003） | B=16, 32 × 6 trial × 2 形式 | **108** |
| リトライ予備（約10%） | (696+108) × 0.1 | **80** |
| **P3 合計（上限）** | 30+696+108+80 | **914** |
| P4 追試予備（承認制・§2.4） | 右打ち切り追試・H4 検出力向上・第2モデル等 | **500** |
| 未割当バッファ | 3,000 − 914 − 500 | **1,586** |

- 8月の月次枠 3,000 req に対し、P3 で最大 **914 req（30.5%）** を上限とする
- B=32 のリクエスト単位指標は形式あたり n=18（両形式合計 36）と粗い。**アイテム単位指標（形式あたり n=576）を主、リクエスト単位指標は参考値**として扱う（限界として記事に明記）
- B=1 は 1 trial のため trial 間ばらつきが出ない。C(1) は temperature=0 でほぼ決定的であり問題ないが、その旨を記事に明記

### 2.2 実行単位（run_id）と試走チェックリスト

| run_id | 内容 | 予算 |
|---|---|---|
| `p3-001` | 試走（下記チェックリスト） | ≤30 |
| `p3-002` | 本実験: B∈{1,2,4,8} | ≤696+リトライ |
| `p3-003` | 大バッチ: B∈{16,32} × 6 trial | ≤108+リトライ |

試走 p3-001 で必ず確認すること（本実験の前提条件）:
1. `gpt-oss-120b` の実際のモデル ID 表記と利用可否（不可なら D-006 の切替を発動し、見積もりを再提示）
2. **reasoning の挙動**: 思考過程が `content` に混入するか別フィールド（`reasoning_content` 等）か。抑制パラメータ（`reasoning_effort` 等）が受理されるか。`usage` の出力トークン数の実態
3. **max_tokens の校正**: B=32 相当の実測最大出力トークン × 安全係数 3 を全水準共通の固定値として決定
4. `finish_reason` の値の観察（`length` 切断が起きていないか）
5. `temperature=0.0` が受理されるか
6. 429 発生時のレスポンスヘッダー（`Retry-After` の有無）
7. **データ難度の確認**: B=1 少数サンプルの正解率が天井（98%超）なら紛らわしい 36 件を差し替え
8. **消費カウントの突合**: コントロールパネルの消費表示とローカルログの件数が一致するか（429/5xx が枠にカウントされるかも観察。sakura-ai スキルの要確認事項）

### 2.3 中断条件

- 429 が 3 連続 → 停止（リトライ上限より優先）
- 同一条件でトランスポート失敗が 5 回（リトライ上限）→ その条件を failed と記録して先へ進む（無限再試行しない）
- チェックポイントにより再開時は未処理分のみ実行（消費の二重計上なし）

### 2.4 P4 予備枠の条件分岐（発動時は再見積もり→承認）

| 条件 | 追試内容 | 概算 |
|---|---|---|
| C(B) が B=32 まで単調減少（右打ち切り） | B ∈ {48, 96} を 6 trial × 2 形式で追試（(2+1)×6×2） | 36 req |
| H4 が未検出かつ検出力を上げたい | B=32 を追加 6 trial × 2 形式 | 36 req |
| 余枠が大きい場合の拡張 | 第2モデル（llm-jp）で B∈{1,8,32} の縮約版 | 〜300 req |

## 3. 交絡・バイアスへの対処

| 懸念 | 対処 |
|---|---|
| アイテムの難度がバッチ間で偏る | trial ごとにシード付きシャッフル。pos 効果の分析はアイテム難度で層別 |
| 時間帯による API 挙動の変動 | 各 trial 内で全水準・全形式を回しきる実行順にし、水準間の時間差を最小化。実行日時をログに記録 |
| 順序効果（ウォームアップ等） | 水準の実行順を trial ごとにローテーション |
| プロンプト差による不公平（H6） | 指示文は共通テンプレートから生成し、形式指定部分だけ差し替え。シャッフルシードは形式間で共有（対応付き比較） |
| max_tokens 切断と B の交絡 | 全水準共通の固定 max_tokens（試走で校正）+ finish_reason 別カテゴリ集計 |
| 正解ラベルの曖昧さ | データ自作でラベルを一意に。作成時にサブエージェントでラベル妥当性レビュー。難度は試走で実測確認 |
