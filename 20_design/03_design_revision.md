# 03. 実験設計の改訂（実測に基づく）

改訂日: 2026-07-29 / 根拠: 試走 p3-001、探索 p3-000・p3-000b の実測（合計66リクエスト）
旧設計: `02_experiment_design.md`（前提が崩れたため本書で置き換える。D-012）

## 1. なぜ設計を変えたか

当初は「バッチサイズを上げると出力が壊れ始め、実効コスト C(B) が U 字になる」と予想し、B=1〜32 を測る計画だった。試走と探索でこの前提が**明確に否定された**。

### 実測1: 軽い出力なら壊れない（p3-000、18リクエスト）

タスク「レビューを positive/negative に分類してラベルだけ返す」で、B=48 と B=96 を各3試行・2形式:

| B | 形式 | パース成功 | アイテム回収 | 正解率 | 切断 | C(B) |
|---|---|---|---|---|---|---|
| 48 | json_array | 6/6 | 288/288 | 100% | 0 | 0.0208 |
| 48 | jsonl | 6/6 | 288/288 | 100% | 0 | 0.0208 |
| 96 | json_array | 3/3 | 288/288 | 100% | 0 | **0.0104** |
| 96 | jsonl | 3/3 | 288/288 | 100% | 0 | **0.0104** |

C(96) = 1/96 は**理論限界**（1リクエストで96件すべて正解）。U 字の右側が存在せず、B* は観測範囲外にある。この設計のまま884リクエストを投じても、既に分かった「単調減少」を精緻に確認するだけになる。

### 実測2: 出力を重くすると崖から落ちる（p3-000b、30リクエスト）

同じデータで、要求する出力だけを重くした:

| タスク | 出力内容 | B=8 | B=32 | B=96 |
|---|---|---|---|---|
| `label` | ラベルのみ | 100% | 100% | **100%** |
| `label_reason` | ラベル + 根拠20〜40字 | 100% | 100% | **0%**（全損） |
| `structured` | ラベル + 根拠 + 確信度 + 観点配列 | 100% | 100% | **40.6%**（部分回収） |

B=96 の2件はいずれも `finish_reason = "length"`（max_tokens 8192 での切断）。**壊れる原因は「モデルが混乱すること」ではなく「出力トークン予算の枯渇」だった。**

### 実測3: 崩壊には2つのモードがある

切断された2件の中身を確認したところ、質的に異なる壊れ方をしていた。

**モードA: reasoning 枯渇（全損）** — `label_reason` B=96
`content` の長さが **0文字**。8,192トークンすべてを reasoning（思考）が消費し、本文の出力に到達しないまま打ち切られた。1リクエストで96件を失う最悪のケース。

**モードB: 出力途中の切断（部分回収）** — `structured` B=96
39件目の途中で切れていた（`..."confidence":0.90,` で終端）。JSONL 形式だったため、**完成していた39件は回収できた**。同じ状況で JSON 配列だったら配列が閉じず全損していたはずで、ここに形式差が現れる。

補足として、この部分回収ケースの C(96) = 1/39 = 0.0256 は、C(32) = 3/96 = 0.0312 より**まだ小さい**。6割を失ってもなお、バッチングした方が実効コストは低い。

### 実測4: reasoning のオーバーヘッドはバッチで償却される

アイテムあたりの出力トークン数:

| タスク | B=8 | B=32 |
|---|---|---|
| `label_reason` | 278.8 tok/件 | 167.8 tok/件 |
| `structured` | 256.3 tok/件 | 217.2 tok/件 |

reasoning はバッチ全体で概ね一定量かかるため、B を上げるほどアイテムあたりに薄まる。これがバッチングの効きの正体の一つ。

## 2. 改訂後の中心的な問い

> **バッチングの限界は出力トークン予算で決まる。ではその崖はどこにあり、どう落ちるのか。**

実務的には、次の見積もり式が使えるかを検証することになる。

```
最適バッチサイズ B* ≈ (max_tokens − reasoning余裕) ÷ アイテムあたり出力トークン
```

## 3. 改訂後の仮説

| ID | 仮説 | 検証方法 |
|---|---|---|
| **H1'** | C(B) は崖に達するまで単調減少し、崖で不連続に悪化する（滑らかな U 字ではない） | タスク×B で C(B) を実測し、`finish_reason=length` の発生位置と重ねる |
| **H2'** | 構造崩れの主因は `finish_reason=length` であり、切断のないリクエストではほぼ発生しない | 切断の有無で層別した破損率 |
| **H3'** | 崖の位置はアイテムあたり出力トークン数で決まり、`max_tokens ÷ トークン/件` で近似できる | 3タスクの実測トークン数から崖位置を予測し、実測と比較 |
| **H4'** | 切断時、欠落はバッチ後方に集中する（前方は完成済み） | `per_item` の pos 別回収率。**誤答ではなく欠落で位置効果を見る**（旧 H4 は誤答ゼロで検証不能だった） |
| **H5'** | アイテムあたりレイテンシは B とともに減少し、reasoning オーバーヘッドの償却で説明できる | latency_ms ÷ B を B で層別 |
| **H6'** | **崖では JSONL が JSON 配列より多くのアイテムを回収する**（部分回収の有無が決定的な差になる） | 切断が起きたリクエストに限定した形式別回収率 |

**H6' が脇役から主役に変わった。** 崖の手前では両形式とも完璧で差が出ないが、崖では「部分回収できるか全損か」という質的な差になる。実測3ですでにその兆候が出ている。

## 4. 改訂後の実験計画（p3-100）

| 要因 | 水準 |
|---|---|
| タスク（出力の重さ） | `label` / `label_reason` / `structured` |
| バッチサイズ B | 8, 16, 32, 48, 96 |
| 出力形式 | `json_array` / `jsonl` |
| 試行 | 2 trial（シードでバッチ構成を変える） |
| `max_tokens` | 8192 固定（全水準共通。B との交絡を避ける） |

1セルあたり 96/B の合計 = 12+6+3+2+1 = **24 req**
24 × 3タスク × 2形式 × 2試行 = **288 req**（上限 700 req に設定、リトライ余裕込み）

小さい B（1, 2, 4）を落とした理由: 試走で完璧と確認済みであり、リクエスト数が高く（B=1 だけで96 req）、崖の観測に寄与しないため。基準線 C(1) は試走 p3-001 の実測（12/12 正解）を使う。

## 5. 消費計画

| run | 内容 | 実績/計画 | 枠 |
|---|---|---|---|
| p3-001 | 試走 | 18 req（実績） | 7月 |
| p3-000 | 探索（B=48, 96） | 18 req（実績） | 7月 |
| p3-000b | 探索（出力の重さ） | 30 req（実績） | 7月 |
| p3-100 | 本実験 | 288 req（上限700） | 7月 |
| **合計** | | **354 req（上限766）** | 7月枠3,000の12%（上限でも26%） |

承認済みの総量（914 req）を下回る。**8月枠3,000 req は全額が追試・拡張用に温存される**（`max_tokens` を変えて崖が移動するかの検証、モデル間比較など）。

## 6. 旧設計から引き継ぐもの

- 採点規則（重複IDは最初の1件、未送信IDは無視、ラベルは正規化）
- リトライ規約（429/5xx/タイムアウトのみ、コンテンツ失敗はリトライしない）
- write-ahead ログとチェックポイント
- プール比による C(B) 算出、形式別の報告
- 限界の明示（同一96アイテムの反復使用、特定モデル・特定時期の実測であること）
