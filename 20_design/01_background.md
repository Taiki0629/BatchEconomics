# 01. 背景・課題定義

作成: 2026-07-28（P1）/ 事実の確認日は個別に記載

## 1. 何を検証するのか（一言で）

**リクエスト数で課金（制限）される LLM API では、複数アイテムを1リクエストに詰める「バッチング」が経済合理的になるはずだが、どこまで詰めると壊れるのか。その損益分岐点＝最適バッチサイズの決め方を実測で明らかにする。**

対象はさくらのAI Engine の基盤モデル無償プラン（Chat completions **3,000 リクエスト/月**。2026-07-27 公式確認、出典は `90_resources/official_docs/00_sources.md`）。

## 2. なぜこの検証が必要か

### 2.1 トークン課金が生んだ設計常識

OpenAI・Anthropic などの主要 LLM API は入出力トークン数に比例した課金であり、この前提で次の設計が常識になっている:

- **1アイテム1リクエスト**に分割する（感情分類 100 件なら 100 リクエスト）
- 分割の利点: 出力が単純になり壊れにくい、失敗時のリトライが 1 アイテム分で済む、並列化しやすい、コンテキストが短く精度が安定する
- 分割のコスト: トークン課金では**ほぼゼロ**。100 件を 100 回に分けても合計トークンは（システムプロンプトの重複を除き）ほとんど変わらない

つまり「分割はタダ同然でメリットだけがある」が、トークン課金世界の結論だった。

### 2.2 リクエスト課金では常識が反転する

さくらのAI Engine の無償枠は**リクエスト数**でカウントされる（トークン数ではない）:

| 項目 | 内容 | 確認日 |
|---|---|---|
| Chat completions 無償枠 | 3,000 リクエスト/月 | 2026-07-27 |
| 超過時の挙動（無償プラン） | 自動課金なし・レート制御がかかる | 2026-07-27 |
| 1リクエストのトークン量による課金差 | 無償プランでは**なし**（リクエスト数のみ） | 2026-07-27 |

この世界では**リクエストこそが希少資源**になる:

- 1アイテム1リクエストの常識設計 → 月 3,000 アイテムで頭打ち
- 1リクエストに B アイテム詰める → 理論上、月 3,000 × B アイテム処理できる
- つまりバッチサイズ B は無償枠の価値を B 倍にする「レバー」に見える

### 2.3 ただしバッチングはタダではない

B を大きくすると、次の劣化が起きる（と予想される）:

1. **構造崩れ**: 出力が長く複雑になり、JSON として壊れる確率が上がる。パース失敗は**そのリクエストの B アイテム全部が無駄**になり、実運用でリトライすればさらにリクエストを消費する（※本実験ではコンテンツ失敗をリトライせず失敗率を直接測定し、リトライ運用時のコストは実測失敗率からのモデル計算で示す。D-008）
2. **アイテム欠落・対応ズレ**: B 件頼んだのに B-1 件しか返らない、ID の対応がズレる
3. **精度低下**: 一度に多数の指示を処理するとアイテム単位の正解率が下がる。特にバッチ後方の位置で劣化する可能性（長文脈で中間・後方の情報利用が弱まるという報告は Lost in the Middle（Liu et al., 2023）などで知られるが、「出力タスクのバッチ内位置効果」への転移は本実験で確かめる）
4. **max_tokens の天井**: 出力が長くなり途中で切れる
5. **失敗の高価格化**: B が大きいほど 1 回の失敗・リトライで失うものが大きい

したがって「詰めれば詰めるほど得」ではなく、**歩留まりを織り込んだ実効コストには最適点があるはず**。これを実測で示すのが本プロジェクトの核心である。

### 2.4 一般性（なぜ無償枠ユーザー以外にも意味があるか）

リクエストが希少資源になる状況は無償枠に限らない:

- **RPM（リクエスト/分）制限**に張り付いているワークロード
- リクエスト単位の固定オーバーヘッド（接続、キュー待ち、プロンプトの定型部）が大きい場合
- リクエスト数ベースの社内クォータ・API ゲートウェイ

本実験の枠組み（実効コスト＝消費リクエスト数 ÷ 正しく処理できたアイテム数）はこれらにもそのまま適用できる。ただし**実測はさくらのAI Engine に対して行い、数値の一般化はしない**（qiita-writing 規約）。

## 3. 中心指標の定義

**実効コスト C(B)** を主指標とする:

```
C(B) = 消費リクエスト数（リトライ含む） / 正しく処理できたアイテム数
```

- 「正しく処理できた」= 出力から復元でき、ID 対応が取れ、かつ内容が正解
- 算出は**プール比**（水準×形式ごとの総消費 ÷ 総正解）を主とし、**形式別に B* を報告**する（詳細定義は `02_experiment_design.md` §1.3）
- C(B) の逆数は「1リクエストあたりの実効歩留まりアイテム数」
- B=1 の C は基準線。ただし本実験の B=1 は比較の一貫性のため B≥2 と同じ構造化出力（JSON）を課しており、「positive」と一語返すだけの素朴な 1 アイテム 1 リクエスト設計より厳しい基準線である（限界として記事に明記）

補助指標: リクエスト単位パース成功率、アイテム返却率、ID 一致率、per-item 正解率（バッチ内位置別）、レイテンシ（リクエスト当たり／アイテム当たり）。

## 4. 仮説 H1〜H6

すべて実測で検証可能な形で立てる。棄却された場合も隠さず記事に書く（qiita-writing 規約）。

| ID | 仮説 | 検証方法（概要） |
|---|---|---|
| **H1** | 実効コスト C(B) は B に対して U 字型（または下に凸）になり、最適バッチサイズ B* > 1 が存在する | B の水準ごとに C(B) を形式別に実測しカーブを描く。B=32 まで単調減少なら B=48, 96 を追試して右側を探す |
| **H2** | 構造崩れは B とともに単調に増加する | 形式ごとに対称な指標で測る: json_array はリクエスト単位パース失敗率、jsonl は行単位破損率。max_tokens 切断由来は別カテゴリ集計 |
| **H3** | アイテム欠落率（items_returned < items_sent）と ID 不一致率は B とともに増加する | 水準ごとの返却率・id_match_rate |
| **H4** | バッチ内位置 pos が後方のアイテムほど per-item 正解率が低い（位置効果） | 復元成功アイテムに限定し、pos 四分位別の正解率を難度で層別。**検出されない場合は検出可能だった効果量の下限を報告する**（本設計の n では小さい効果は検出できない） |
| **H5** | アイテム当たりレイテンシ（リクエスト完了時間 ÷ B）は B とともに減少する（スループットはバッチングで改善） | 成功 attempt の latency_ms ÷ B を B で層別。リクエスト当たりレイテンシは記述的に示すのみ |
| **H6** | プロンプト形式で頑健性が異なる: JSONL（1行1アイテム）は JSON 配列より大きい B で壊れにくい | **形式間で対称に定義したアイテム回収率と C(B)** で比較（リクエスト単位 parse_ok は定義が非対称になるため主指標にしない） |

### 仮説の背景にある読み

- H1: C(B) = B が大きいほど分母（成功アイテム）の伸びが鈍り、失敗の高価格化が効いてくるため。もし失敗率が B に依存しなければ C(B) は単調減少になり「詰め放題が正解」という別の結論になる。**どちらに転んでも記事になる**
- H4: 位置効果が出るなら「重要なアイテムはバッチ前方に置く」という実務 Tips が導ける
- H6: JSONL は 1 行ずつ独立に復元できるため、部分的な構造崩れから**部分回収**できる可能性がある（JSON 配列は 1 文字の崩れで全滅しうる）。「壊れ方の質」の違いも記録する

## 5. スコープ

### やること
- Chat completions API・単一モデル（通常提供モデルから P2 で選定）での B 水準比較
- プロンプト 2 形式（JSON 配列 / JSONL）の比較
- 客観採点可能なタスク（正解が機械判定できるもの）での精度測定

### やらないこと（理由付き）
- 複数モデルの横断比較 → 無償枠予算を1条件の統計的信頼性に集中させる。余枠があれば P4 で拡張判断
- RAG・Embeddings・音声系 API → 主題（リクエスト課金×バッチング）に不要。Embeddings 枠（10,000/月）は使わない
- 有償プランのトークン課金最適化 → 参考計算のみ。実測はしない
- プロンプト圧縮・キャッシュ等の他の節約術 → 記事の焦点がぼける

## 6. 成果物（記事）の想定読者と提供価値

- 想定読者: さくらのAI Engine の無償枠を使う個人開発者・検証中の企業エンジニア。より広くは、レート制限やクォータの下で LLM バッチ処理を設計する人
- 提供価値: (1) 実測に基づく最適バッチサイズの決め方（手順として再利用可能）、(2) バッチが壊れるときの壊れ方のカタログ、(3) 消費リクエストを見積もる計算式と実験コード

## 7. 制約・リスク（P1 時点）

- 無償枠 3,000 req/月が実験の総予算。設計（P2）で配分を決め、承認なしに消費しない
- レート制限の閾値（req/秒）は非公開。実測中に 429 に当たる可能性があり、リトライも枠を消費する
- プレビューモデルは入れ替わりがあるため、通常提供モデル（`gpt-oss-120b` 等）を主対象にする
- `gpt-oss-120b` は reasoning モデルであり、思考トークンが出力予算とレイテンシに影響する。max_tokens は B 非依存の固定値（試走で校正）とし、切断は別カテゴリ集計して交絡を避ける
- 同一 96 アイテムを全条件で再利用するため観測は完全独立ではない。区間はアイテム単位のクラスターブートストラップで示し、その限界を図注に明記する
- 結果は 2026-08 時点・特定モデル・特定タスクでの実測であり、普遍的な最適値ではない（記事に明記する）
