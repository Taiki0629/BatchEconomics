# BatchEconomics

さくらのAI Engine の「リクエスト課金」特性を実測検証し、最適バッチサイズの決め方を明らかにするプロジェクト。成果は Qiita 記事として公開予定。

## 背景（概要）

トークン課金の LLM API では「小さく分けて投げる」設計が一般的だが、さくらのAI Engine の無償枠は **リクエスト数課金**（Chat completions 3,000 req/月 など）。この前提では複数アイテムを1リクエストにまとめる「バッチング」が経済的に有利になる可能性がある。一方でバッチサイズを大きくすると出力の壊れやすさ（パース失敗・アイテム欠落・精度低下）が増えるはずで、その損益分岐点を実測で明らかにする。

## 再現手順

> 実験実装（P3）完了後に確定版へ更新する。以下は現時点の骨子。

1. さくらのAI Engine のアカウントトークンを発行する
   - <https://secure.sakura.ad.jp/ai/> → 「アカウントトークン」→「アカウントトークンを作成」
2. 環境変数を設定する

   ```bash
   cp .env.example .env
   # .env に SAKURA_API_KEY=<UUID>:<シークレット> を記入
   ```

3. Python 環境を構築する（Python 3.11+ / [uv](https://docs.astral.sh/uv/) を使用）

   ```bash
   uv sync
   ```

4. 実験を実行する（スクリプトは `30_development/` に配置予定）

## 注意

- 実験は基盤モデル無償プランの範囲（Chat 3,000 req/月）で設計されている
- API キーをコード・ログ・リポジトリに含めないこと（`.env` は `.gitignore` 済み）
